# Salvador Transcriber — план тестирования

## 1. Цель и обязательные уровни проверки

План проверяет требования [`plans/techincal-task.md`](techincal-task.md) и архитектурные инварианты [`plans/implementation-plan.md`](implementation-plan.md). Испытания делятся на два обязательных, но разных уровня:

1. **Быстрый автоматический набор без сети.** FastAPI, сценарный fake-адаптер, временная SQLite-база и локальный тестовый HTTP-приёмник. Проверяет детерминированную логику и регрессии.
2. **Реальная интеграционная и ручная проверка OpenAI.** Настоящий ключ, настоящий Realtime API, два независимых аудиоканала и аудио в реальном темпе. Подтверждает фактическую транскрибацию, VAD, задержки и восстановление.

Прохождение fake-тестов не засчитывается как прохождение реальных сценариев. Название модели gpt-live-transcribe, аудиоформат, VAD и все точные поля API перед реальным прогоном сверяются с актуальной официальной документацией; тест не должен закреплять выдуманные payload-поля.

## 2. Тестовое окружение и данные

### 2.1. Быстрое окружение

- Временный каталог и отдельная SQLite-база на тест.
- Fake-адаптер с независимым экземпляром на канал и сценариями: нормальные partial/final, дубли, out-of-order revision, задержка чтения, блокировка отправки, разрыв, ошибка reconnect и поздние события старого generation.
- Локальный HTTP-приёмник, который сохраняет headers, idempotency key и payload, умеет возвращать ошибку/таймаут и считать повторы.
- Маленькие лимиты очередей и короткие таймауты для детерминированного воспроизведения overflow и shutdown deadline.
- Генератор PCM16 mono и разрешённые аудиоfixtures; тесты не используют реальный OpenAI-ключ.

### 2.2. Реальное окружение

- Отдельный тестовый ключ передаётся только через окружение; ключ, текст и аудио не коммитятся.
- Зафиксированные версия приложения, конфигурация модели/VAD/очередей/reconnect, дата проверки документации и сетевые условия.
- Два различных голосовых дорожки либо два живых источника. Дорожки содержат легко различимые фразы и не смешиваются перед ingress.
- Demo-client подаёт кадры в реальном темпе и фиксирует monotonic timestamps отправки.
- Локальный HTTP-приёмник Salvador-контракта; настоящий Salvador endpoint используется дополнительно, если предоставлен.
- Средство искусственно закрыть именно клиентский WebSocket к OpenAI во время разговора, не завершая FastAPI и не подменяя адаптер fake.

### 2.3. Минимальный набор fixtures

| Fixture | Содержание | Назначение |
|---|---|---|
| guest_booking | Вопрос гостя о бронировании | Обычный разговор и latency |
| operator_booking | Ответ администратора с другой лексикой | Роль и разделение текста |
| guest_overlap / operator_overlap | Одновременные разные фразы | Одновременная речь |
| guest_short_pause | Одна смысловая фраза с короткой паузой | VAD без лишнего разбиения |
| guest_long_pause | Две смысловые фразы с длинной паузой | Завершение реплики |
| guest_disconnect_before / guest_disconnect_after | Реплики до и после разрыва | Reconnect и сохранность |
| call_a_guest/operator и call_b_guest/operator | Четыре различимые фразы | Два звонка и изоляция hotel_id |
| silence и noise | Тишина и неразборчивый шум | Отсутствие ложных финалов и диагностика |
| pcm_8k / pcm_16k / pcm_48k | Один сигнал на разных частотах | Ресэмплинг и таймлайн |

Для каждой аудиодорожки манифест содержит частоту, длительность, ожидаемую роль, ориентировочные границы речи и допустимую текстовую проверку. Для реального OpenAI допускаются незначительные варианты пунктуации; роль, смысл, отсутствие чужой фразы и финальность проверяются обязательно.

## 3. Быстрые автоматические тесты

### 3.1. Контракты, аудио и состояния

| ID | Проверка | Основные утверждения |
|---|---|---|
| UNIT-01 | Round-trip событий | Обязательные поля сохраняются; неверная роль, отрицательное время и end_ms раньше start_ms отклоняются |
| UNIT-02 | PCM-валидация | Нечётный PCM16-буфер, stereo и неподдерживаемая частота отклоняются без обращения к адаптеру |
| UNIT-03 | Границы кадров | Остаток между WebSocket-сообщениями не теряется; порядок сэмплов сохраняется |
| UNIT-04 | Ресэмплинг | Выходная частота соответствует конфигурации; длительность и границы остаются в документированном допуске; flush учитывает хвост |
| UNIT-05 | Таймлайн | start_ms/end_ms вычисляются по сэмплам; паузы и разные частоты не создают накопленный дрейф |
| UNIT-06 | Состояния канала | Разрешённые переходы работают; события closed/failed канала отбрасываются; второй канал не меняет состояние |
| UNIT-07 | Состояния звонка | Повторные close/stop идемпотентны; реестр удаляет звонок только после освобождения ресурсов |
| UNIT-08 | Ingress | start обязателен; hotel_id неизменен; конфликт владельца роли и неверные сообщения получают понятную ошибку |

### 3.2. Partial/final, дубли и хронология

| ID | Сценарий | Основные утверждения |
|---|---|---|
| EVT-01 | Несколько partial и один final | Все события имеют один utterance_id и sequence; revision растёт; финал последний |
| EVT-02 | Финал без partial | Создаётся одна валидная финальная реплика |
| EVT-03 | Повторный идентичный final | Одна строка SQLite, одно внутреннее финальное событие и один логический экспорт; duplicate counter увеличивается |
| EVT-04 | Повторный final с другим текстом | Первый финал неизменен; конфликт зафиксирован; новой реплики нет |
| EVT-05 | Старый revision после нового | Устаревшее обновление игнорируется; текст не откатывается |
| EVT-06 | Позднее событие старого generation | Событие игнорируется; новый generation не изменяется |
| EVT-07 | Пустой финал | Не экспортируется как содержательная реплика; результат учитывается в метриках согласно контракту |
| EVT-08 | Финалы приходят вне аудиопорядка | Чтение транскрипции сортирует по start_ms, sequence, utterance_id независимо от порядка прихода |
| EVT-09 | Одинаковые start_ms при одновременной речи | Tie-breaker детерминирован; обе реплики сохранены; перекрытие не считается ошибкой |
| EVT-10 | Независимые sequence и utterance_id | sequence монотонен в пределах звонка; счётчики разных звонков и каналов не дают смешанных идентификаторов |

### 3.3. Backpressure, reconnect и gaps

| ID | Сценарий | Основные утверждения |
|---|---|---|
| REL-01 | Медленный OpenAI и заполнение аудиоочереди | Глубина никогда не превышает лимит; применяется drop-new; ingress не блокируется бесконечно |
| REL-02 | Непрерывное переполнение | Последовательные потери объединяются/закрываются по контракту; dropped frames/bytes и gap совпадают |
| REL-03 | Разрыв во время in-flight partial | Канал переходит в reconnecting; старый partial аннулирован; gap сохранён; поздний final старого generation отброшен |
| REL-04 | Успешный reconnect | Создан новый generation; старые финалы неизменны; новая речь даёт новый utterance_id и финал |
| REL-05 | Исчерпание reconnect | Только затронутый канал получает terminal error; процесс, второй канал и другой звонок продолжают работу |
| REL-06 | Аудио во время reconnect превышает буфер | Потеря не скрывается; gap содержит причину и известные границы; память ограничена |
| REL-07 | Медленный экспорт | Аудиоочередь и OpenAI-чтение не блокируются; финал остаётся в SQLite; retry использует тот же idempotency key |
| REL-08 | Переполнение очереди экспорта | Возникает явная ошибка/метрика неотправленного события; сохранённый финал не удаляется и не дублируется |

### 3.4. Завершение и хранение

| ID | Сценарий | Основные утверждения |
|---|---|---|
| LIFE-01 | Нормальный stop | Приём закрыт, остаток дренирован, доступные финалы сохранены, оба адаптера закрыты |
| LIFE-02 | Повторный stop и shutdown | Финалы и call_completed не дублируются; транскрипция побайтово/структурно неизменна |
| LIFE-03 | Один канал завис при закрытии | Дедлайн срабатывает; второй канал закрывается; незавершённый partial получает gap, а не финал |
| LIFE-04 | Shutdown приложения с двумя звонками | Новые звонки отклоняются; все сессии завершаются; задачи и WebSocket не остаются |
| LIFE-05 | Повторное чтение после закрытия | Сохранены только финалы и gaps; partial отсутствуют; порядок стабилен |
| LIFE-06 | Ошибка экспорта при shutdown | Сохранённые финалы не теряются; неотправленный остаток явно отражён в статусе/отчёте |

## 4. Автоматизация пяти сценариев ТЗ на fake

Эти сценарии запускаются в быстром наборе и служат регрессией оркестрации.

### AUTO-S1. Обычный разговор

1. Создать звонок, подключить guest и operator, отправить поочерёдно две дорожки.
2. Fake выдаёт partial и final для каждой фразы.
3. Проверить правильные роли, разные utterance_id, единый call_id/hotel_id, временные метки и хронологию.
4. Проверить guest_utterance_completed, событие оператора и две финальные строки в SQLite.

### AUTO-S2. Одновременная речь

1. Одновременно отправлять разные PCM-потоки в оба канала.
2. Задержать финал одного канала, чтобы сетевой порядок отличался от аудиопорядка.
3. Проверить отсутствие чужого текста, независимые OpenAI-экземпляры и очереди, перекрывающиеся start_ms/end_ms и детерминированную сортировку.

### AUTO-S3. Паузы

1. Подать короткую паузу внутри фразы и длинную паузу между фразами.
2. Fake моделирует VAD-события согласно заданной конфигурации.
3. Проверить отсутствие лишнего разбиения короткой паузы, завершение на длинной и корректные границы.
4. Отдельно проверить, что изменение VAD-конфигурации валидируется и попадает в параметры адаптера без дублирования в домене.

### AUTO-S4. Обрыв OpenAI с восстановлением

1. Сохранить финал до разрыва, начать следующую partial и закрыть fake-соединение.
2. Во время reconnect подать аудио, включая вариант с overflow.
3. Проверить ошибку, попытки восстановления, неизменность старого финала, gap, новый generation и финал после восстановления.
4. Проверить продолжение работы operator и отсутствие зависших задач.

### AUTO-S5. Два независимых разговора

1. Запустить call_a/hotel_a и call_b/hotel_b одновременно, с разными фразами и задержками.
2. Проверить четыре независимых ChannelSession, отсутствие перекрёстных событий и отдельные sequence.
3. Попытаться подключить канал call_a с hotel_b и получить отказ.
4. Завершить один звонок и убедиться, что второй продолжает принимать и сохранять реплики.

## 5. Обязательные проверки с настоящим OpenAI

### 5.1. Общие критерии реального прогона

Для каждого сценария сохраняются: идентификатор прогона, дата, проверенное имя модели, VAD/аудио/reconnect-конфигурация, роли, количество partial/final, финальная транскрипция или разрешённая обезличенная выдержка, gaps, метрики, latency/recovery и результат.

Общие условия успеха:

- используется настоящий Realtime API и два отдельных соединения на звонок;
- получены реальные partial и финальные реплики, а не заранее записанные ответы fake;
- роли и call_id/hotel_id корректны, чужой текст отсутствует;
- каждая содержательная реплика финализируется один раз и сохраняется;
- ошибки и потери не скрываются; отчёт включает неуспешные попытки.

### REAL-S1. Обычный разговор

**Шаги:** подать вопрос гостя, дождаться финала, затем подать ответ оператора; завершить звонок штатно.

**Ожидания:** обе стороны распознаны по смыслу; guest и operator не перепутаны; partial обновляют соответствующую реплику; финалы имеют временные метки; события Salvador сформированы; SQLite содержит две финальные реплики и не содержит partial.

**Доказательства:** транскрипция, события HTTP-приёмника, count финалов/дублей, latency каждой реплики и отсутствие ошибок закрытия.

### REAL-S2. Одновременная речь

**Шаги:** запустить разные фразы гостя и оператора одновременно с заметным перекрытием; повторить с обратным порядком завершения.

**Ожидания:** каждая фраза остаётся в своём канале; перекрытие по времени допускается; ни одна реплика не исчезает из-за активности другого канала; финалы могут прийти в другом порядке, но хронология восстанавливается.

**Доказательства:** совмещённый таймлайн двух ролей, четыре независимых идентификатора соединений/каналов в диагностике, отсутствие смешанного текста и latency по ролям.

### REAL-S3. Паузы

**Шаги:** подать фразу с короткой паузой, затем две фразы с длинной паузой; при необходимости повторить с другой документированной настройкой VAD.

**Ожидания:** короткая пауза не создаёт необоснованные две финальные реплики; длинная пауза завершает высказывание; настройки VAD реально применены; задержка финала измерена, а не оценена визуально.

**Доказательства:** границы аудио и реплик, использованные VAD-параметры, число финалов и latency. Если поведение модели отличается, зафиксировать факт и предложить калибровку без подмены результата.

### REAL-S4. Обрыв OpenAI с восстановлением

**Шаги:** получить финал до разрыва; начать следующую речь; искусственно закрыть WebSocket guest к OpenAI; продолжать подавать аудио; дождаться reconnect; подать новую различимую фразу; штатно завершить звонок.

**Ожидания:** ошибка обработана без падения приложения; operator продолжает работать; выполнены наблюдаемые попытки reconnect; финал до разрыва сохранён; новая фраза распознана после восстановления; неполный участок обозначен gap, а не склеен; старый generation не создаёт дубль.

**Доказательства:** t_disconnect/t_detected/t_ready/t_first_new_final, попытки и ошибки, dropped frames/bytes, gap, финалы до/после и состояние operator. Если восстановление неуспешно, сценарий не отмечается пройденным, но все измерения сохраняются.

### REAL-S5. Два независимых разговора

**Шаги:** одновременно запустить call_a/hotel_a и call_b/hotel_b, у каждого свои guest/operator и разные фразы; варьировать паузы; завершить звонки в разное время.

**Ожидания:** четыре независимых канала и четыре OpenAI-сессии; нет перекрёстного текста, идентификаторов, gaps или состояний; завершение call_a не влияет на call_b; каждая SQLite-транскрипция содержит только свой звонок.

**Доказательства:** две отдельные транскрипции, события с двумя hotel_id, метрики активных звонков/каналов и отсутствие роста ресурсов после закрытия.

## 6. Дополнительные обязательные проверки в реальном прогоне

- **Дубли:** повторная доставка одного нормализованного финала в finalizer/хранилище не создаёт повторную запись; реальный OpenAI не обязан искусственно дублировать событие, поэтому детерминированная проверка остаётся автоматической.
- **Переполнение:** реальный прогон с намеренно маленьким буфером выполняется только контролируемо; обязательное доказательство — ограниченная глубина, dropped counter и gap. Основная полная матрица остаётся на fake.
- **Изоляция call_id/hotel_id:** REAL-S5 обязателен; попытка сменить hotel_id отклоняется в AUTO-S5 и при возможности повторяется вручную.
- **Финализация ровно один раз:** число финальных записей совпадает с числом уникальных utterance_id; повторный stop не меняет результат.
- **Хронология:** экспортированная полная транскрипция отсортирована по контракту даже при одновременной речи и разном порядке финалов.
- **Сохранение финалов:** после reconnect, stop и повторного чтения SQLite все финалы до разрыва доступны без изменений.
- **Фиксация потери аудио:** при REAL-S4 любой пропущенный участок имеет gap; если потери не было, это подтверждается отсутствием dropped frames и непрерывностью принятого аудиотаймлайна, а не просто отсутствием gap.

## 7. Методика измерения задержек

### 7.1. Сбор наблюдений

Для каждой финальной реплики записывается отдельное наблюдение:

- run_id, scenario, call number, role и anonymized utterance number;
- длительность аудио и паузы;
- t_speech_end_ingress, t_final_internal, t_export_sent и t_export_ack на одной monotonic шкале;
- final_latency_ms и export_latency_ms;
- reconnect flag, VAD-конфигурация и признак валидности наблюдения.

Основная формула: final_latency_ms = t_final_internal − t_speech_end_ingress. Время до HTTP-подтверждения отчитывается отдельно. Нельзя измерять от конца всего аудиофайла, если реплика закончилась раньше, и нельзя использовать ускоренную подачу файла.

### 7.2. Выборка и агрегаты

- Для REAL-S1, REAL-S2 и REAL-S3 в совокупности целевая выборка — не менее 20 финалов на роль при нормальном соединении; если исходные записи не позволяют, указать фактический count.
- Отдельно агрегировать guest/operator, каждый сценарий и общий нормальный набор.
- Указывать count, min, median, p95, max и процент наблюдений не более 2000 мс.
- Не удалять медленные валидные наблюдения. Ошибки распознавания и reconnect исключаются из нормальной latency-статистики с явным count и причиной.
- Цель MVP: p95 не более 2000 мс при нормальном соединении. Недостижение цели фиксируется как результат, а не скрывается изменением выборки.

### 7.3. Восстановление

Для REAL-S4 отчёт содержит detection_delay, reconnect_duration, время до первого нового финала, число попыток, длительность/границы gap и dropped frames/bytes. Успех определяется совокупностью: процесс жив, второй канал работает, старые финалы сохранены, новый финал получен, потери явны. Конкретный бюджет восстановления берётся из зафиксированной reconnect-конфигурации и прикладывается к отчёту.

## 8. Критерии завершения тестирования

- [ ] Все быстрые unit/integration/fake-сценарии проходят повторно без сети и без незавершённых задач.
- [ ] Все пять REAL-сценариев выполнены с настоящим OpenAI; любой пропуск имеет причину и не считается успехом.
- [ ] Дубли, overflow, изоляция call_id/hotel_id, финал ровно один раз, хронология, сохранение финалов и gaps покрыты явными assertions.
- [ ] Два независимых разговора показаны одновременно, а не последовательно.
- [ ] Реальные partial/final и VAD подтверждены; fake не указан как доказательство интеграции.
- [ ] Latency-отчёт содержит сырые наблюдения, выборку, агрегаты и долю до 2 секунд.
- [ ] Recovery-отчёт содержит времена, попытки, сохранённые финалы, новый финал и потери/gaps.
- [ ] Все сбои, ограничения и отклонения от целевых значений внесены в итоговый отчёт.

## 9. Структура итогового отчёта

Заполняется [`docs/test-report.md`](../docs/test-report.md):

1. Версия кода, дата, окружение и ссылка на проверенную документацию OpenAI.
2. Конфигурация модели, аудио, VAD, очередей, reconnect, shutdown и экспорта без секретов.
3. Таблица AUTO/REAL сценариев: статус, фактический результат, ссылка на доказательства.
4. Отдельная таблица обязательных инвариантов: дубли, overflow, изоляция, финал, хронология, persistence, gaps.
5. Сырые latency-наблюдения и агрегаты по ролям/сценариям.
6. Recovery-хронология и измерения для каждого обрыва.
7. Ошибки OpenAI/HTTP/SQLite, неуспешные попытки и их обработка.
8. Невыполненные требования: причина, влияние и конкретное техническое решение.
9. Итог: соответствие Definition of Done и известные ограничения MVP.
